Animation & transitions

Motion that responds to state changes (transitions) versus motion that runs on its own timeline (animations) - and how to keep both running at 60fps.

transition vs animation

transitionanimation
TriggerA property value changing (hover, class toggle, JS)Runs automatically once applied, on its own timeline
StatesTwo — start and endAny number, via @keyframes
LoopingNoYes, with animation-iteration-count
Typical useHover states, focus states, togglesLoaders, entrance sequences, looping effects

Transitions

transitions.css
.button {
  transition: background-color 0.2s ease, transform 0.15s ease;
}
.button:hover {
  background-color: #93b4fa;
  transform: translateY(-2px);
}
transition: all is a footgun

transition: all 0.2s; transitions every animatable property that changes - including ones you didn't intend, like layout shifts from unrelated JS. List properties explicitly for predictable, cheaper transitions.

Transform

transform.css
transform: translate(20px, -10px);
transform: scale(1.05);
transform: rotate(8deg);
transform: skew(-4deg);
transform: translate(-50%, -50%); /* combined with top/left: 50% — perfect centering */
transform-origin: top left; /* pivot point for scale/rotate, default is center */

Transforms don't affect document flow or trigger layout recalculation in sibling elements - which is exactly why they're the performant choice for movement, over animating top/left/margin.

Keyframe animations

keyframes.css
@keyframes pulse {
  0%, 100% { opacity: 1; }
  50%       { opacity: 0.4; }
}

.skeleton {
  animation: pulse 1.6s ease-in-out infinite;
}

/* shorthand order: name duration timing-function delay iteration-count direction fill-mode */
.entrance {
  animation: slide-up 0.4s ease-out 0.1s 1 normal both;
}

animation-fill-mode: both is easy to forget and causes a common bug: the element snaps back to its pre-animation state (or flashes unstyled) right before the animation starts, or right after it ends, because the animation's styles don't apply outside its active duration by default.

Timing functions

FunctionFeel
easeDefault - starts fast, slows at the end. Good general-purpose choice.
ease-inSlow start, fast finish - good for elements leaving the screen
ease-outFast start, slow finish - good for elements entering the screen
linearConstant speed - good for continuous loops (spinners, marquees)
cubic-bezier(x1,y1,x2,y2)Fully custom curve, including overshoot/bounce effects

Performance: what to animate

Browsers can animate transform and opacity on the compositor thread, off the main thread, so they stay smooth even while JavaScript is busy. Animating width, height, top, left, or margin triggers layout recalculation on every frame, which is far more expensive.

will-change, used sparingly

will-change: transform; hints the browser to promote an element to its own compositor layer ahead of time. Apply it right before an animation starts and remove it after - leaving it on permanently wastes memory on every layer it creates.

Interview angle

Q: Why are transform and opacity considered the "safe" properties to animate? They can be handled by the compositor without triggering layout or paint on every frame, unlike properties that affect box geometry. Be ready to name which properties are cheap vs expensive. More in the interview guide.
