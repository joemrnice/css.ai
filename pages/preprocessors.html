Sass/SCSS basics

_base.scss
$brand: #7aa2f7;   // compile-time variable
$spacing: 1rem;

.card {
  padding: $spacing;
  border: 1px solid;

  &:hover { border-color: $brand; } // nesting

  .dark & { background: #111; } // & anywhere in the selector
}

Sass variables don't exist at runtime - they're substituted by the compiler, so nothing about them can respond to media queries, JS, or the cascade the way a CSS custom property can.

Mixins & functions

_mixins.scss
@mixin button-variant($bg, $fg: white) {
  background: $bg;
  color: $fg;
  &:hover { background: darken($bg, 8%); }
}

.btn-primary { @include button-variant(#7aa2f7); }
.btn-danger  { @include button-variant(#f7768e); }

Mixins are Sass's answer to "generate a batch of related rules from shared logic" - loops (@each, @for) are commonly used to generate spacing/color utility classes from a map.

Partials & @use

main.scss
@use 'base';       // loads _base.scss, namespaced as base.$brand etc.
@use 'components/card';
@forward 'mixins';   // re-export for files that @use this one

@use replaced the older @import - it namespaces variables/mixins by file instead of dumping everything into one shared global scope, avoiding name collisions across a large project.

Less, briefly

Less predates Sass's dominance and uses @ for variables instead of $, with similar nesting and mixin support. It's less commonly chosen for new projects today, but still powers some legacy codebases (older Bootstrap versions were built on it before switching to Sass).

PostCSS & autoprefixer

PostCSS isn't a language like Sass - it's a plugin-based tool that transforms CSS you already wrote. The most common plugin, autoprefixer, adds vendor prefixes (-webkit-, -moz-) automatically based on a target browser list, so you write standard CSS and never hand-write prefixes.

postcss.config.js
module.exports = {
  plugins: [
    require('autoprefixer'),
    require('postcss-preset-env')({ stage: 1 }) // use tomorrow's CSS syntax today
  ]
};

What you still need a preprocessor for

Native CSS closed a lot of gaps (nesting, variables, math with calc()), but preprocessors still offer things CSS doesn't have: real loops and conditionals, string manipulation functions, and the ability to generate entire rule sets from a data map at build time.

Interview angle

Q: Now that CSS has native nesting and variables, is Sass obsolete? No - name a concrete thing Sass still does that CSS can't: compile-time loops over a data structure, mixins with default parameters and complex logic, or generating a whole utility set programmatically.
