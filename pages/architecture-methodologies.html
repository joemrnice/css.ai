Architecture & methodologies

Naming conventions and file organization exist to solve one problem: keeping specificity and selector scope predictable as a codebase grows past a handful of files.

BEM - Block, Element, Modifier

BEM keeps every class name flat and self-describing, so specificity stays uniform (every selector is a single class) and there's never ambiguity about what a class belongs to.

bem.css
/* block__element--modifier */
.card               { } /* block */
.card__title        { } /* element - a part of the block */
.card__title--large { } /* modifier - a variant */
.card--featured     { } /* modifier on the block itself */
card.html
<div class="card card--featured">
  <h3 class="card__title card__title--large">Title</h3>
</div>

Trade-off: verbose class names, and no built-in answer for layout/spacing utilities - teams usually pair BEM with a small utility layer.

SMACSS - Scalable and Modular Architecture for CSS

SMACSS categorizes rules into five types rather than prescribing a naming convention:

  • Base - element defaults, no classes (e.g. a { color: blue; })
  • Layout - major page regions, often prefixed l- or layout-
  • Module - reusable components (cards, buttons, nav)
  • State - a module's condition, prefixed is- (e.g. .is-active, .is-collapsed)
  • Theme - visual variations that can be swapped independently of structure

ITCSS - Inverted Triangle CSS

ITCSS organizes stylesheets by specificity and reach rather than by component, ordering files so each layer has broader scope but lower specificity than the one after it - solving load-order fights before they start.

itcss layers, in load order
1. Settings   /* variables, config - no output */
2. Tools      /* mixins, functions - no output */
3. Generic    /* resets, box-sizing - broad, low specificity */
4. Elements   /* bare tag styles: h1, a, ul */
5. Objects    /* layout patterns, no cosmetics: .o-container */
6. Components /* actual UI pieces: .c-button, .c-card */
7. Utilities  /* single-purpose overrides: .u-hidden, !important allowed here */

Modern cascade layers (@layer, see modern CSS) let you express this same ordering natively, without relying on file concatenation order.

Utility-first CSS

Instead of naming components, compose styles from small, single-purpose classes directly in markup - the approach popularized by Tailwind CSS (see the frameworks guide).

utility-first.html
<div class="flex items-center justify-between p-6 rounded-lg bg-slate-900">

Trade-off: markup carries more visual detail and can look noisy, but there's no CSS file to grow unbounded, no naming decisions to make, and dead styles are easy to spot (unused classes just stop appearing in markup).

Choosing an approach

SituationReasonable fit
Large team, many contributors, need enforceable namingBEM
Big legacy codebase, need a clear file/load-order strategyITCSS + cascade layers
Fast product iteration, small design system already definedUtility-first (Tailwind)
Small project, few contributorsLightweight component-scoped CSS - full methodology may be overkill
Interview angle

Q: Why would a team choose Tailwind over BEM, or vice versa? Frame it as a trade-off between markup verbosity and stylesheet growth, not "which is objectively better" - a strong answer names the actual constraint (team size, design system maturity, iteration speed) that would tip the decision.
